# ccscan — 读完整个项目，把它变成一张想法图

先读引擎旁边的 FORMAT.md（`node .companion/companion.mjs paths` 会打印所有
规范路径；规范文件就在引擎同目录）。

## 参数

一个路径把扫描范围限定到那个目录；`--refresh` 是在现有图上补，而不是推倒
重来。不带参数就是整个项目、从头建一张图。

## 第 0 步 — 先看有没有旧图要迁

```
node .companion/companion.mjs migrate --dry-run
```

发现旧格式的图（带 agent 后缀的 YAML、一节点一文件的 JSON）就先停下：把干跑
报告给人看，让人决定 `migrate` 还是 `--pick` 哪一份。多份旧图并存时命令自己会
停下要求人选择 —— 这不是故障，是规矩：绝不自动挑赢家。迁移完成或确认无旧图，
才开始扫描。

## 第 1 步 — 建扫描清单

```
node .companion/companion.mjs scan
```

清单是程序生成的（git 追踪的加未忽略的新文件，跳过依赖目录和二进制）。
**划掉一行的唯一方式是真的读它** —— 读文件的事件由 hook 记账（D12），你自己说
「读过了」不算数。`scan` 随时重跑可以看剩余。

## 第 2 步 — 读到清单归零

逐个读，**不许抽样**。顺序是后面的解释前面的：先 README、CLAUDE.md、AGENTS.md
和 docs（写着意图），再配置和依赖清单（写着真实结构），再全部源码含测试（测试
比任何散文都更准确地说出第 3 问的预期结果），最后 git log（意图藏在提交信息里，
尤其是骂人的那几条）。

读不完就如实报告读了多少、剩多少 —— 剩余数字是程序算的，报告里不许出现和它
对不上的说法。被跳过的文件（vendor、生成物）也要列出来并说明为什么（D29）。
读了一半的图比没有图更糟，因为它看起来是完整的。

## 第 3 步 — 问人：什么叫「这个项目做完了」

用提问工具给人三到五个终点候选，让人选定 endpoints。终点不是你定的。

## 第 4 步 — 提取想法，建图

每个想法回答前三问（是什么 / 为什么 / 预期结果），能答八问的答八问。
新建想法一律用引擎发号：

```
node .companion/companion.mjs new "一句人话的名称" --needs I-001
```

图上每句话都必须让没打开过这个仓库的人看懂 —— 写它做什么，不写它叫什么。

**答不出来就留空，绝不编。** 这四栏是最容易被编出来的：

- `why_this_way` 是你最想撒谎的地方。真实理由在注释、提交信息和设计文档里；
  找不到就写 `why_this_way: null`，并把这个想法列进最后的报告。编出来的理由
  会被下一个 agent 当成事实，然后一路捍卫下去。
- `code` 必须解析得到：真实文件、真实行号（D32）。ccfix 完全信这一栏。
- `verify` 只写真的存在的东西：有测试就写那条测试，没有就用 `manual` 写清人
  该看什么。**绝不编造一条不存在的验证命令。**
- `expected` 从测试和文档里读；两处都没说，就问人，或者如实标成未答。

## 第 5 步 — 渲染，停下

```
node .companion/companion.mjs check
node .companion/companion.mjs render
```

`check` 报的错要在给人看之前全部修掉。然后把网页路径给人，按顺序报告：
真实的扫描数字（读了几个、跳过几个、剩几个）、终点和各自有多少想法通向它、
按状态分的计数和当前前沿、**以及 `why_this_way` / `expected` / `verify` 没
答上来的想法逐个列出** —— 这份清单是下一轮 ccthink 的议程，也是这条工作流
最值钱的产物。

报告完就停下等人审。不要在人看图之前接着做任何事。这条工作流只写想法图、
网页和 log，不碰产品代码、不建测试、不重构任何东西。
